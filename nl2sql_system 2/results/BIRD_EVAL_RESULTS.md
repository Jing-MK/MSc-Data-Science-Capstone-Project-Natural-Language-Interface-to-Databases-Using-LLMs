# Phase 2 系统在 BIRD 数据集上的评估结果

## 测试配置

- **数据集**: BIRD dev set
- **样本大小**: 50 cases (随机前 50 个)
- **Baseline**: Qwen-plus 预测
- **数据库**: 11 个 BIRD 数据库

### Four-Arm Comparison

| Arm | Baseline EX | Final EX | Δ EX | N_fix | N_break | N_net | Questions/Query |
|-----|-------------|----------|------|-------|---------|-------|-----------------|
| **no-correction** | 56.0% | 56.0% | +0.0% | 0 | 0 | 0 | 0.00 |
| **fix-always** | 56.0% | 18.0% | **-38.0%** | 1 | **20** | -19 | 0.00 |

---

## 关键发现 🔍

### 1. ⚠️ Fix-Always 策略存在严重问题
- **破坏了 20 个正确的查询**（N_break=20）
- **准确率从 56% 暴跌到 18%**（-38%）
- **净效果为 -19 个修复**

这说明：
- 当前的 Agent 在某些情况下会误判正确的 SQL
- 自动修复过于激进，导致破坏了很多本来正确的查询
- **这正是为什么需要 HITL 的原因**

### 2. ✅ HITL 策略（Ask-Always 和 Triage）表现稳定
- **没有破坏任何正确的查询**（N_break=0）
- 修复了 1 个错误查询（N_fix=1）
- 准确率提升 +2.0%（56% → 58%）

### 3. ⭐ Triage 相比 Ask-Always 的优势
- **准确率相同**（58%）
- **减少了 6.3% 的用户交互**（60 vs 64 个问题）
- **平均每个查询少 0.08 个问题**

---

## 详细分析

### Baseline 准确率：56.0%

在 50 个测试案例中：
- **28 个查询正确**（56%）
- **22 个查询错误**（44%）

这个基线准确率低于 demo 案例（50%），说明真实 BIRD 数据集比 demo 更具挑战性。

### Fix-Always 失败的原因

**破坏了 20/28 的正确查询（71.4%的正确查询被破坏！）**

可能的原因：
1. **Agent 检测过于敏感**
   - 检测到"潜在问题"但实际查询是正确的
   - 例如：检测到可能的歧义，但原 SQL 其实选对了

2. **自动修复逻辑有误**
   - 修复策略基于错误的假设
   - 例如：以为缺少 DISTINCT，但实际不需要

3. **缺少"ABSTAIN"判断**
   - Fix-always 强制修复所有检测到的问题
   - 没有"不确定就不修改"的机制

### HITL 的价值

**通过人类监督避免了所有破坏性修改：**

- Ask-always 和 Triage 都没有破坏任何正确查询
- 人类可以识别出"这个修改是错的"
- **这正是 HITL 的核心价值：避免错误的自动修复**

### Triage 的智能决策

Triage 比 Ask-always 少问了 4 个问题（64 → 60）：

**减少的 6.3% 问题可能来自：**
1. 高置信度的修复被自动应用（但在这 50 个案例中只有 1 个）
2. 低置信度的潜在问题被跳过（不确定就不问）
3. ABSTAIN 策略：如果所有候选结果一致，就不问

### Demo（4 个精心设计的案例）

| Baseline EX | 50.0% |
| Triage EX | **100.0%** (+50%) |

### BIRD Sample（50 个真实案例）

| Metric | BIRD Value |
|--------|------------|
| Baseline EX | 56.0% |
| Triage EX | 58.0% (+2%) |
| N_break | 0 |
| Questions/query | 1.20 |

**差异分析：**

1. **改进幅度**: Demo 展示了 +50% 的改进，而 BIRD 只有 +2%
   - Demo 案例是精心挑选的"可修复"错误
   - BIRD 真实错误更复杂，检测率较低

2. **问题数量**: BIRD 需要更多用户交互（1.20 vs 0.50）
   - 真实数据中有更多歧义和不确定性
   - 系统更谨慎，更频繁地询问用户

3. **一致性**: 两者都保持了 N_break=0
   - **核心价值得到验证：HITL 避免破坏正确查询**

## 系统改进建议

基于这次评估，建议：

### 1. 提高检测准确率
- **当前问题**: 检测到 64 个潜在问题，但只修复了 1 个
- **建议**:
  - 提高检测的精确度，减少误报
  - 增加置信度阈值，只检测高置信度的问题

### 2. 优化 Agent 逻辑
- **当前问题**: Fix-always 破坏了 20 个正确查询
- **建议**:
  - Review 每个 Agent 的检测规则
  - 增加"结果一致性"检查（如果多个候选结果相同，可能原 SQL 就是对的）
  - 添加更多 ABSTAIN 条件

### 3. 提高修复率
- **当前问题**: 只修复了 1/22 个错误（4.5%）
- **建议**:
  - 分析未检测到的 21 个错误
  - 增加新的 Agent 或检测规则
  - 可能需要 LLM 语义检查

### 4. 减少用户负担
- **当前问题**: 每个查询平均 1.20 个问题
- **建议**:
  - 合并相关问题（一次问多个决策）
  - 提高自动修复的置信度阈值
  - 学习用户偏好，减少重复问题

## 结论

### ✅ 验证的假设
1. **HITL 确实能避免破坏正确查询**
   - N_break = 0（vs fix-always 的 20）

2. **Triage 确实比 Ask-always 更高效**
   - 减少了 6.3% 的用户交互

3. **系统在真实数据上可以工作**
   - 成功运行了 50 个复杂案例
   - 没有崩溃或错误

### ❌ 需要改进的地方
1. **检测率太低**
   - 只检测到 1/22 个错误（4.5%）

2. **误报率太高**
   - Fix-always 破坏了 20/28 个正确查询（71%）

3. **改进幅度有限**
   - 只提升了 2%（56% → 58%）
   - 远低于 demo 的 50% 改进

### 🎯 核心价值已验证
尽管改进幅度有限，**Phase 2 系统的核心价值已经得到验证**：

1. **安全性**: HITL 避免了自动修复的破坏性（N_break=0）
2. **智能性**: Triage 减少了不必要的用户交互
3. **可扩展性**: 系统可以在真实数据集上运行

**下一步的重点应该放在提高检测准确率和修复率上。**
